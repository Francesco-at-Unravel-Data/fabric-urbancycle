# Naming Conventions

All Microsoft Fabric items in the UrbanCycle project use a type prefix followed by a descriptive `snake_case` name. Prefixes are `lh_` for lakehouses, `wh_` for warehouses, `md_` for mirrored databases, `pl_` for pipelines, `cj_` for Copy Jobs, `nb_` for notebooks, `df_` for Dataflow Gen2, `env_` for environments, `vl_` for Variable Libraries, `sm_` for semantic models, and `rpt_` for reports. Examples include `lh_urbancycle`, `wh_control`, `pl_bronze_ingest`, `nb_silver_trip_conform`, `sm_urbancycle_core`, and `rpt_urbancycle_operations`. Tables and columns use `snake_case`; table names are singular and descriptive, such as `fact_trip` and `dim_station`. Columns use clear names such as `station_id`, `station_sk`, `started_at_utc`, and `trip_duration_minutes`; units are included when omitting them would make a value ambiguous. Technical audit and lineage columns are the exception and begin with `_`, for example `_batch_id` and `_ingested_at_utc`. SCD2 tables use `valid_from_utc`, `valid_to_utc`, `is_current`, and `attr_hash`.

UrbanCycle is implemented as one schema-enabled lakehouse, `lh_urbancycle`, representing the UrbanCycle analytical data product. Schemas identify the medallion processing layer and use `bronze`, `silver`, and `gold`, so each level of the namespace has a distinct responsibility: the lakehouse identifies the data product, the schema identifies the processing layer, and the table identifies the dataset or analytical entity. Fully qualified examples are `lh_urbancycle.bronze.trip_raw`, `lh_urbancycle.silver.trip`, and `lh_urbancycle.gold.fact_trip`. The processing layer is not repeated in the table name, so use `bronze.trip_raw`, `silver.trip`, and `gold.fact_trip` rather than names such as `bronze.bronze_trip_raw`, `silver.silver_trip`, or `gold.gold_fact_trip`. The Fabric-created `dbo` schema is treated as the default platform namespace and is not used for UrbanCycle lakehouse application tables; project lakehouse tables are written explicitly to `bronze`, `silver`, or `gold`. Source systems do not receive dedicated lakehouse schemas. Source identity is instead represented through ingestion paths, lineage metadata, technical audit columns, and control metadata. Raw files in `lh_urbancycle` use the convention `Files/bronze/<source>/<dataset>/ingest_date=YYYY-MM-DD/`, for example `Files/bronze/citibike/tripdata/ingest_date=2026-08-12/` and `Files/bronze/open_meteo/hourly/ingest_date=2026-08-12/`.

Control tables live in `wh_control` under `dbo` and use singular descriptive names such as `load_watermark`, `run_log`, `dq_result`, and `source_registry`. Naming exceptions are limited to namespaces where the audience or tooling differs: workspaces use `PascalCase-Environment` such as `UrbanCycle-Dev`, DAX measures use consumer-readable `Title Case` such as `Trips YoY %`, security roles use `RLS_<Scope>` such as `RLS_Borough`, and repository documentation uses `kebab-case` such as `naming-conventions.md`. SQL and Python files use `snake_case`, and notebook files use the same base name as their Fabric item. Git uses `main`, `dev`, and `feature/<short-description>` branches, with commits in the form `<type>: <imperative summary>`, using types such as `feat:`, `fix:`, `refactor:`, `docs:`, `test:`, and `ci:`.
